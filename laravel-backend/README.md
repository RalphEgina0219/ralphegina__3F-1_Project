# LaundryFlow API (Laravel)

The REST API behind LaundryFlow, the laundry shop management and QR basket tracking system.
The React frontend in `../react-frontend` talks to it.

It follows the Web Systems course **"API Master Class in Laravel"**: see
[`../docs/COURSE_CONVENTIONS.md`](../docs/COURSE_CONVENTIONS.md) for every convention and the
conflicts that were resolved. In short:

- **Routes:** versioned at `/api/v1` (`routes/api_v1.php`).
- **Authentication:** JWT, with separate guards for staff and customers.
- **Responses and requests:** JSON:API-style resources and request bodies.
- **Lists:** `QueryFilter` classes handle filtering and sorting.
- **Authorization:** Policies, checked with `isAble()`, and abilities written into the token.
- **Errors:** one format, `{ errors: [{ status, message, source }] }`.
- **Documentation:** generated by Scribe.

The endpoint list is in [`../docs/API_INVENTORY.md`](../docs/API_INVENTORY.md). The database
diagram is in [`../docs/ERD.md`](../docs/ERD.md).

## Requirements

- PHP 8.3+ with `pdo_mysql`, `mbstring`, `openssl` and `intl` (recommended).
- Composer 2.
- MySQL 8 or MariaDB 10.6+. Laragon and XAMPP both work. MySQL is required: the reports use
  `CONVERT_TZ`/`DATE()` and the `order_baskets` table has a generated column.
- Node 20+, for the React app only.

## Run the whole system in 5 minutes (Laragon)

The project lives in `C:\laragon\www\Final_Project_WST&AppDev`. Adjust the paths below if yours
differs.

1. **Start Laragon** (Start All): MySQL and Apache.
2. **The virtual host** `http://laundryflow.test` → `laravel-backend/public`. Laragon's automatic
   hosts follow folder names, and `&` cannot be in a host name, so add one by hand:
   - copy [`../docs/laragon/laundryflow.test.conf`](../docs/laragon/laundryflow.test.conf) to
     `C:\laragon\etc\apache2\sites-enabled\laundryflow.test.conf`;
   - add `127.0.0.1 laundryflow.test` to `C:\Windows\System32\drivers\etc\hosts` (Notepad as
     administrator), or let Laragon do it with Menu › Apache › Reload;
   - Menu › Apache › Reload.
3. **The API** (Laragon's Terminal):

   ```bash
   cd laravel-backend
   composer install
   cp .env.example .env            # APP_URL=http://laundryflow.test, DB_* for Laragon's root user
   php artisan key:generate
   php artisan jwt:secret
   mysql -uroot -e "CREATE DATABASE IF NOT EXISTS laundryflow; CREATE DATABASE IF NOT EXISTS laundryflow_test"
   php artisan migrate:fresh --seed  # about 10 seconds: reference data + 120 days of history
   ```

   Check it: <http://laundryflow.test/api/v1/customer/barangays> lists 36 barangays, and
   <http://laundryflow.test/docs> opens the API docs.
4. **The app:**

   ```bash
   cd ../react-frontend
   npm ci
   npm run dev                      # http://localhost:5173, /api proxied to laundryflow.test
   ```

5. **Sign in** at <http://localhost:5173/login> as `liza.ramos` / `password123` (the owner), or as
   a customer at `/my/login` with `maria.santos@example.com` / `password123`.

No Apache or no hosts entry? `php artisan serve` still works: Vite falls back to
`http://127.0.0.1:8000` by itself when `laundryflow.test` does not resolve (set
`API_PROXY_TARGET` in `react-frontend/.env.development.local` to force one or the other).

## Setup (Laragon or XAMPP)

1. Start MySQL in Laragon or XAMPP.
2. Create the databases. Example for MySQL on 127.0.0.1:3306 as `root` with no password:

   ```sql
   CREATE DATABASE laundryflow CHARACTER SET utf8mb4 COLLATE utf8mb4_unicode_ci;
   CREATE DATABASE laundryflow_test CHARACTER SET utf8mb4 COLLATE utf8mb4_unicode_ci;
   ```

3. Install the packages and configure the app:

   ```bash
   cd laravel-backend
   composer install
   cp .env.example .env          # then check DB_* (and FRONTEND_URL)
   php artisan key:generate
   php artisan jwt:secret        # JWT_SECRET, which signs the tokens
   php artisan migrate:fresh --seed
   php artisan serve             # http://127.0.0.1:8000
   ```

`migrate:fresh --seed` takes about 10 seconds. It loads the reference data and 120 days of shop
history. `database/seeders/DemoSeeder.php` is a deterministic port of the frontend's
`mocks/seed.ts`: the same generator and seed, giving the same orders, customers, charts and
reports.

## Running both apps together

With Laragon's virtual host (above), only the frontend needs a terminal:

```bash
cd react-frontend && npm ci && npm run dev           # http://localhost:5173
```

Without it, start the fallback server too:

```bash
# terminal 1
cd laravel-backend && php artisan serve              # http://127.0.0.1:8000
# terminal 2
cd react-frontend && npm run dev
```

Vite proxies `/api` to `http://laundryflow.test` when that name resolves, otherwise to
`http://127.0.0.1:8000` (`API_PROXY_TARGET` overrides both). The browser sees one origin, so CORS
is not involved in development. `npm run dev` and `npm run build` use this API. Only
`npm run build:demo` and the frontend's unit tests still use the in-browser mock.

## Performance on Windows

`php artisan serve` is PHP's built-in server: one request at a time, and slow to start each one on
Windows. A dashboard asks for 8 things at once, so they queue. Laragon's Apache runs PHP as a
thread-safe module and answers them in parallel. Measured on the demo seed (Windows 11, Laragon,
MySQL 8.4, OPcache on):

| | `php artisan serve` | Laragon Apache |
| --- | --- | --- |
| 8 dashboard requests at once (wall time) | 1,198 ms | 575 ms |
| One public request (`/customer/barangays`), warm | ~500 ms before OPcache | 40 ms |

**OPcache.** In `C:\laragon\bin\php\php-8.3.*\php.ini` (Menu › PHP › php.ini), uncomment
`zend_extension=opcache` and set `opcache.enable=1`, `opcache.memory_consumption=128`,
`opcache.interned_strings_buffer=16`, `opcache.max_accelerated_files=20000`. Keep
`opcache.validate_timestamps=1` and `opcache.revalidate_freq=2` while developing, so edits show
within 2 seconds. Then reload Apache. Check with `php -m` (it lists `Zend OPcache`).

**For a demo run** (no code changes expected), cache the framework's bootstrap:

```bash
php artisan optimize        # config:cache, route:cache, event:cache and view:cache in one go
php artisan optimize:clear  # before changing code or .env again
```

With the cache on, `.env` is read only when the cache is rebuilt, so run `optimize` again after
editing it. `composer test` clears the config cache itself.

**Queries.** Every list endpoint answers a page with a fixed number of queries, whatever the page
size: the user and role, the page, its count, the summary figures and one query per included
relation (`tests/Feature/QueryCountTest.php` checks 5 rows against 50, at most 15 queries; the
reports and dashboard at most 25). The slowest endpoints after the fixes, median of 5 calls through
Apache on the demo seed:

| Endpoint | Time |
| --- | --- |
| `GET /analytics/dashboard` (30 days, with comparison) | 377 ms |
| `GET /reports/staff` (30 days) | 343 ms |
| `GET /reports/{payments,services,customers,orders,sales}` (30 days) | 250–270 ms |
| `GET /dashboard/summary` | 229 ms |
| `GET /balances` | 218 ms |
| `GET /customers` | 209 ms |
| `GET /orders` (the board: every active order) | 156 ms |
| `GET /orders` (a page of 15) | 120 ms |
| `GET /payments`, `/baskets`, `/activity-logs`, `/inventory/items` | 50–95 ms |

Before the fix, an order list ran 75 queries for 15 rows and the board 159: `withMoney()` aliased
its sub-selects with `addSelect(['alias' => DB::raw(…)])`, which ignores the key, so every order
summed its payments again.

### Real concurrency test

`tests/Concurrency/OrderRaceTest.php` fires truly simultaneous HTTP requests (`Http::pool`, one
curl_multi batch) at a running server:

- 10 "take in an order" requests for the **same basket**: exactly one is 201, the other nine are
  409 "BSK-… is in use by LF-…", and none is a database error;
- then 20 orders on the same day, each with its own basket: all 201, with 20 different numbers that
  follow the winner's without a gap (the nine refused orders used up no number).

It is not part of `composer test`: it needs a server that runs requests in parallel (Laragon's
Apache, not `php artisan serve`) and it writes to that server's database.

```bash
php artisan migrate:fresh --seed
RACE_URL=http://laundryflow.test php artisan test tests/Concurrency
# without a hosts entry:
RACE_URL=http://127.0.0.1 RACE_HOST=laundryflow.test php artisan test tests/Concurrency
```

How the API stays correct under it (`app/Actions/V1/CreateOrder.php`): one transaction that first
locks the day's row in `order_sequences`, then the chosen baskets (`lockForUpdate()`), checks
them, and only then draws the order number. Orders of one day therefore pass one at a time (a few
milliseconds each), locks are always taken in the same order, and a refused order never draws a
number. `DB::transaction(…, attempts: 3)` retries on a deadlock, and the unique index on
`order_baskets (basket_id, active_flag)` backs it all up with a 409 of its own. The first version of
this test caught two deadlocks that reached the client as 500s: `INSERT IGNORE` on an existing
sequence row, and two orders locking neighbouring gaps of the `order_baskets` index.

## API documentation (Scribe, course L26)

```bash
php artisan scribe:generate   # the docs page, the Postman collection and the OpenAPI file
php artisan docs:postman      # docs/api/: the collection with its login-token script, and the OpenAPI copy
```

Then open:

- `http://laundryflow.test/docs`: the docs page, with Try It Out. Paste a token from
  `POST /api/v1/auth/login`.
- `http://laundryflow.test/docs.postman`: Scribe's raw Postman collection.
- `http://laundryflow.test/docs.openapi`: the OpenAPI file.

**Postman.** Import [`../docs/api/laundryflow.postman_collection.json`](../docs/api/laundryflow.postman_collection.json).
It needs no setup on a freshly seeded database: a collection pre-request script signs in as
`liza.ramos` (staff folders) or `maria.santos@example.com` (customer portal folders) whenever it has
no token, and stores it in `{{token}}` / `{{customerToken}}`. "Log in" stores a new token and
"Log out" forgets it. The list requests remember real ids for the requests after them, and "Take in
an order" makes the following order requests use the new order. Change `baseUrl` (default
`http://laundryflow.test`) for `php artisan serve`. Run from the command line with
`npx newman run ../docs/api/laundryflow.postman_collection.json`. On a fresh seed, 74 of the 80
requests succeed; the other six show rules on purpose: retiring a basket in use, a second account
for a customer, voiding a payment on a completed order (409), and the three password changes,
which send a wrong current password so the demo accounts keep `password123` (422).

To include real example responses, set `SCRIBE_AUTH_KEY` to a staff token before generating.
The calls run inside a transaction that is rolled back. Customer-portal examples are `@response`
tags recorded with a customer token.

Scribe records that token in its cache (`.scribe/endpoints/*.yaml`). Before committing, replace
it with `{YOUR_AUTH_KEY}` and blacklist it (`POST /api/v1/auth/logout` with it). The committed
docs were generated that way.

## Deployment notes

- **HTTPS everywhere.** Phones need it for the camera and the PWA, and tokens must never travel
  in clear text.
- **Same origin:** serve the built React app and this API from one domain, with `/api` going to
  Laravel (Nginx `location /api { try_files … /index.php }`). No CORS then.
- **Separate API origin:** set `VITE_API_URL=https://api.example.com/api/v1` when building the
  frontend, and `FRONTEND_URL=https://app.example.com` here (CORS, `config/cors.php`). The API
  uses Bearer tokens, not cookies, so no Sanctum or session domain settings are needed.
- **Time zone:** keep `APP_TIMEZONE=Asia/Manila` and `DB_TIMEZONE=+08:00`. Reports group by
  Manila day.
- **Frontend caching:** serve the frontend's `sw.js`, `manifest.webmanifest` and `index.html` with
  `Cache-Control: no-cache`. Hashed files under `/assets/` can be cached for a year. The service
  worker never caches `/api/`.
- **Tokens:** `JWT_TTL` (minutes, default 60) and `JWT_REFRESH_TTL` (minutes, default 14 days).
  The app refreshes an expired token once and signs out if that fails. Logout and refresh
  blacklist the old token (stored in the cache, so keep `CACHE_STORE` persistent).

### Production `.env` checklist

- [ ] `APP_ENV=production`, `APP_DEBUG=false`. Debug off hides file names and messages in 500
      errors.
- [ ] `APP_KEY` set (`php artisan key:generate`), and `JWT_SECRET` set (`php artisan jwt:secret`).
      Never reuse the development ones.
- [ ] `APP_URL` is the public HTTPS URL. `FRONTEND_URL` is the React app's origin.
- [ ] `DB_*` point at the production database, with a dedicated user that is not root.
- [ ] `APP_TIMEZONE=Asia/Manila`, `DB_TIMEZONE=+08:00`.
- [ ] `CACHE_STORE=database` or `redis`, so the JWT blacklist and rate limits survive restarts.
- [ ] `LOG_LEVEL=warning` or higher.
- [ ] Run `php artisan migrate --force`, then `php artisan db:seed --class=ReferenceDataSeeder`
      only once. It inserts the roles, services, statuses, units, supply items and the shop profile,
      plus the four demo staff accounts with `password123`: change those passwords or disable the
      accounts at once. Do **not** run the demo seeder (`DemoSeeder`, `db:seed`) in production.
- [ ] Run `php artisan optimize` (config, routes, events and views cached) after every deploy.
- [ ] OPcache on, with `opcache.validate_timestamps=0` (reload PHP after each deploy).

## Production hardening

What is in place, and what the server must add.

- **HTTPS only.** Put both sites behind HTTPS and redirect port 80 to 443 at the web server; add
  `Strict-Transport-Security: max-age=31536000` there. With `APP_ENV=production` the API writes
  every link as `https://` (`URL::forceHttps()` in `AppServiceProvider`). Phones need HTTPS anyway
  for the camera and the installable app.
- **Tokens.** Access tokens live 60 minutes (`JWT_TTL`). An expired one can be exchanged for a new
  one until 14 days after the original sign-in (`JWT_REFRESH_TTL`, counted from the first token:
  `refresh_iat` stays off), then the user signs in again. Logout and refresh blacklist the token.
  A disabled account is refused on its next request, whatever its token says, and a revoked
  permission stops at once. The secret is only in `.env` (`JWT_SECRET`, generated per server).
- **Errors.** `APP_DEBUG=false` in production: a crash answers `500 "Server error"` with no
  message, class, file or line. Deliberate answers (409, 429…) never carry a file, even in debug.
- **CORS.** Only the origins in `FRONTEND_URL`, only the methods and headers the app uses, no
  credentials (`config/cors.php`). Same-origin deployments need none.
- **Rate limits** (tested in `SecurityTest` and `AuthTest`): staff and customer sign-in 5 failures
  a minute per name and IP; customer self-registration 10 a minute per IP; scanning 120 a minute per
  staff member and IP; token refresh 30 a minute per IP.
- **Mass assignment.** Every model declares `#[Fillable]`, and controllers save only a Form
  Request's `mappedAttributes()`, which keeps just the fields the request maps. Unknown body keys
  (`roleId`, `mustChangePassword`, `id`…) are ignored (tested).
- **No secrets in answers.** `User` and `CustomerAccount` hide `password`; no resource has a
  password, hash or token field (tested against every account endpoint).
- **Validation on every write.** Form Requests, or `request()->validate()` for the few actions
  without one.
- **Dependencies.** `composer audit`: no advisories. `npm audit --omit=dev` (frontend): two
  moderate advisories in `react-router` 6.x, fixed only in 7.x (a breaking upgrade, not done):
  - *Open redirect via a backslash in `<Link>` / `navigate`:* the only place the app navigates to
    a URL it did not write is `?next=` after sign-in; `safeNext()` refuses anything but a same-site
    path, backslashes and control characters included (tested).
  - *`deserializeErrors()` in SSR hydration:* does not apply, as the app renders in the browser only.
