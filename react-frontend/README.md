# LaundryFlow frontend

A web-based laundry shop management system with basket QR tracking and customer accounts, for a
startup laundry business in Bongabong, Oriental Mindoro.

It runs against the **Laravel API** in [`../laravel-backend`](../laravel-backend) (JWT, the course's
JSON:API-style responses under `/api/v1`). The in-browser mock API (MSW) from Phase 1 is kept for the
static demo build (`npm run build:demo`) and the unit tests. To run the whole system, follow
**"Run the whole system in 5 minutes"** in [`../laravel-backend/README.md`](../laravel-backend/README.md).

**How tracking works.** Every load goes into one or more reusable **baskets**. Each basket has a
permanent QR label that only staff scan. There is **no printed receipt** and **no public tracking
page**: every order belongs to a registered customer, who follows it in their own account at
`/my`, where the digital **Order Summary** replaces the receipt.

## Setup

Requires Node 20 or newer, and the Laravel API running (Laragon's Apache at
`http://laundryflow.test`, or `php artisan serve`).

```bash
npm ci
npm run dev
```

Open <http://localhost:5173>. Vite proxies `/api` to `http://laundryflow.test` when that name
resolves (Laragon, fast and parallel), otherwise to `php artisan serve` at `http://127.0.0.1:8000`.
`API_PROXY_TARGET` forces either. Without any server, `npm run build:demo && npm run preview` runs
the app on the in-browser mock.

### Statuses

Received → Washing → Drying → Folding → Ready for Pickup → **Completed**. The last stage keeps the
internal code `released`; only its label is "Completed". It needs a zero balance, releases the
order's baskets, and makes the transaction read-only for everyone, admins included (409).

### Real-time updates

The customer pages re-fetch every 15 seconds, on window focus and on reconnect, and show
"Last updated" with a manual refresh. There are no WebSockets in Phase 1. Laravel Reverb broadcasting
on a private `customer.{id}` channel is an optional Phase 2 upgrade that needs no screen changes.

## Install LaundryFlow as an app

LaundryFlow is a Progressive Web App: staff and customers can install it on a phone, tablet or laptop.
It then opens from its own icon in its own window, without the browser's address bar.

**Android (Chrome, Edge, Samsung Internet).** Open the site and tap **Install app**: in the staff menu
(sidebar or **More**), under the sign-in form, or on **My account**. On the second visit a banner also
suggests it. Or use the browser menu **⋮ › Install app** (older versions: **Add to Home screen**).
Long-press the icon for the shortcuts **Scan QR**, **New order** and **My laundry**.

**iPhone and iPad (Safari).** iOS has no install prompt. Tap **Share**, then **Add to Home Screen**,
then **Add**. The **Install app** button shows these steps.

**Desktop (Chrome, Edge).** Click the install icon at the right of the address bar, or **Install app**
in the sidebar.

The installed app starts at `/`. A device that last used the customer portal goes to `/my` instead of
the staff sign-in.

### Updates

The app checks for a new version when it opens, every hour, and whenever its window regains focus.
When one is ready, a toast stays on screen, **A new version of LaundryFlow is available**, with
**Reload** and **Later**. Nothing reloads by itself. If a form on screen has unsaved changes (a new
order, a payment, a customer, the shop profile, a registration), **Reload** asks first. The version
number is under **Settings › Shop profile › About LaundryFlow**.

### What works offline

LaundryFlow handles money, statuses and personal data, so offline support is deliberately narrow:

- **The app itself opens offline.** Its code, styles, icons and fonts are stored on the device, so
  even a page never visited before opens.
- **Data already on screen stays visible**, and the offline banner says when it was last updated.
- **Nothing is saved offline.** Every button that saves (orders, statuses, payments, stock, settings,
  sign-in) is blocked with an explanation, and API requests are never cached or queued. When the
  connection returns, the screen refreshes and says **Back online**.
- **Signing out always works.** It clears this device's cached data and recent scans, so the next
  person on a shared shop phone sees nothing of the last one's.
- If a page's code can't be downloaded, `/offline` explains and offers **Retry**.

### Service workers: demo build vs real API

A site can have only one service worker per scope, and MSW (the mock API) is one. So:

| Build                                          | Service worker                           | Installable | Offline app shell |
| ---------------------------------------------- | ---------------------------------------- | ----------- | ----------------- |
| `npm run dev`, `npm run build:demo` (mocks on) | MSW's `mockServiceWorker.js` only        | Yes         | No                |
| `npm run build` (mocks off, real API)          | Workbox `sw.js` only; MSW is not shipped | Yes         | Yes               |

`src/main.tsx` registers exactly one of them, after removing the other mode's leftover worker (and,
in the demo, any old Workbox caches). A demo build's `sw.js` only unregisters itself, so a device that
once ran a real-API build at the same address cleans up on its own.

Running Workbox inside MSW's worker (`importScripts`) was considered and left out. Both answer every
request, and MSW only works from its own script, so the demo would lose either its mocks or its cache.

## The Laravel API (Phase 2, connected)

`npm run dev` and `npm run build` use the Laravel API in `../laravel-backend`. Setup, demo
accounts and deployment are in [`../laravel-backend/README.md`](../laravel-backend/README.md).
In development, Vite proxies `/api` to Laragon (`http://laundryflow.test`) or, when that name does
not resolve, to `php artisan serve` (`http://127.0.0.1:8000`); `API_PROXY_TARGET` overrides both.

```
VITE_USE_MOCKS=false
VITE_API_URL=/api/v1                # or https://api.example.com/api/v1 (then set FRONTEND_URL there)
VITE_PUBLIC_URL=https://your-domain
```

**How the frontend talks to it.** The API follows the course "API Master Class in Laravel"
([`../docs/COURSE_CONVENTIONS.md`](../docs/COURSE_CONVENTIONS.md)):

- JWT Bearer tokens, with separate tokens for staff and customers;
- JSON:API-style resources with camelCase attributes, and request bodies of the form
  `{ data: { attributes, relationships } }`;
- errors as `{ errors: [{ status, message, source }] }`;
- course-style filters (`receivedAt=from,to`);
- PATCH for partial edits.

One adapter, [`src/lib/apiAdapter.ts`](src/lib/apiAdapter.ts), turns all of that back into the
screens' contract below. It is applied by the interceptors in `src/lib/api.ts`, so no component
changed. Tokens live in `src/lib/tokens.ts`. On a 401, the client refreshes the token once
(`/auth/refresh` or `/customer/auth/refresh`) and retries; if that fails, it signs out.

**The mock stays** for `npm run build:demo` (a static demo with no server) and for the unit and
integration tests in `src/mocks/*.test.ts`, which still speak the contract below directly. The
removal steps (delete `src/mocks/`, `public/mockServiceWorker.js`, the `msw` dependency, the mock
branch in `src/main.tsx` and the **Reset demo data** card) wait until the team confirms. Keep
`removeOtherWorkers('pwa')`: it removes the MSW worker from phones that ran the demo.

**Errors on screen.** `src/lib/apiAdapter.ts` turns `{ errors: [{ status, message, source }] }`
into `{ message, errors: { field: [msg] } }`:

| Status | What the user sees                                                                                                                                                                                                                                       |
| ------ | -------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| 401    | One silent token refresh, then the sign-in page (`/login` or `/my/login`) with `?next=`                                                                                                                                                                  |
| 403    | The API's message in a toast; a page the role may not open shows the 403 page. A pending password change (`Change your temporary password first.`) re-reads the account and opens the change-password page                                               |
| 404    | "Order not found" (or the list's empty state) on detail pages; a toast for actions                                                                                                                                                                       |
| 409    | The API's message word for word ("BSK-0007 is in use by LF-…", "This basket has no active laundry session.", "This transaction is completed.", "Orders move one stage at a time. Next is Washing."). On the new-order form it also appears under Baskets |
| 422    | Each message under its own field (`applyFieldErrors`, with a rename step for forms whose fields differ from the body, such as the new-order form and the reason dialogs)                                                                                 |
| 429    | The API's own wording, or "Too many attempts. Please wait a minute and try again."                                                                                                                                                                       |
| 5xx    | Always "Something went wrong on our side. Please try again in a moment." Whatever the server sent (with `APP_DEBUG=true`, the exception text) never reaches the screen                                                                                   |

**Staff password.** After the owner resets a staff password (Settings › Users & roles › Reset
password, shown once with a copy button), that account opens only `/password` until a new one is
saved; Sign out still works. The same page is "Change password" in the account menu (the user card
at the bottom of the sidebar). It reuses the customer's password frame (`PortalAuthShell`) and form
(`PasswordForm`).

**Contract check:** `npm run test:contract` reseeds Laravel, starts `php artisan serve`, builds the
real-API app and runs every `*.contract.spec.ts` plus `analytics.demo.spec.ts` against it:

| Spec                           | What it covers                                                                                                                                                                  |
| ------------------------------ | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| `contract.spec.ts`             | Sign-in, the main lists, scanning, the portal, and the staff password reset → forced change → normal access                                                                     |
| `errors.contract.spec.ts`      | One example of each status: 401, 403, 404, 409, 422, 429 and 500                                                                                                                |
| `walkthrough.contract.spec.ts` | Every screen as owner, staff and customer at 390 px and 1440 px: no sideways scroll, no error state, no console error                                                           |
| `flows.contract.spec.ts`       | Counter to pickup with the customer watching; self-registration; permissions; every dashboard preset and report; settings and baskets; the installed app and its service worker |
| `analytics.demo.spec.ts`       | The dashboard and reports against Laravel's numbers                                                                                                                             |

While iterating, `CONTRACT_REUSE=1 npm run test:contract` reuses servers you already started

Serve `sw.js`, `manifest.webmanifest` and `index.html` with `Cache-Control: no-cache`, over HTTPS.
The service worker never caches `/api/` and never answers it with the app shell.

### Screens' contract (what the adapter produces)

Everything in `src/types/api.ts`, with these conventions: snake_case JSON, ISO-8601 timestamps, money as
integer centavos (`*_cents`), lists as `{ data, meta: { current_page, per_page, total, last_page } }`,
validation failures as `422 { message, errors: { field: [msg] } }`, missing session as `401`, missing
permission as `403`, a rule the record's state breaks as `409 { message }`. Single resources are
returned **without** a `data` wrapper (`JsonResource::withoutWrapping()`).

### Analytics endpoints

The dashboard and the seven reports read two endpoints. Both take a Manila date range (inclusive)
and compare against the range of the same length just before it.

| Endpoint                                                                        | Ability                | Query                                                                                                           |
| ------------------------------------------------------------------------------- | ---------------------- | --------------------------------------------------------------------------------------------------------------- |
| `GET /analytics/dashboard`                                                      | `dashboard.view`       | `from`, `to` (`yyyy-MM-dd`, default the last 30 days), `compare=previous\|none`                                 |
| `GET /reports/{sales\|orders\|payments\|services\|customers\|inventory\|staff}` | `reports.view` (admin) | as above, plus filters: `service`, `method`, `status`, `staff`, `barangay`, `item`                              |
| `GET /orders`                                                                   | `orders.manage`        | drill-downs add `waiting_min`, `waiting_max` (days in the current status) and `due` (`yyyy-MM-dd` or `overdue`) |

Every response has the same envelope (types in `src/lib/analytics/types.ts` and `build.ts`):

```json
{
  "range": { "from": "2026-10-09", "to": "2026-11-07" },
  "compare_range": { "from": "2026-09-09", "to": "2026-10-08" },
  "generated_at": "2026-11-07T07:41:00.000Z",
  "kpis": [
    {
      "key": "sales",
      "label": "Sales",
      "format": "money",
      "value": 11396800,
      "previous": 9618000,
      "delta_pct": 18.5,
      "spark": []
    }
  ],
  "series": { "sales": [{ "date": "2026-10-09", "value": 287500, "previous": 251000 }] },
  "table": {
    "columns": [{ "key": "date", "label": "Date", "format": "date" }],
    "rows": [],
    "totals": {}
  },
  "insights": ["Sales rose 18.5% compared with the previous 30 days."]
}
```

Rules the Laravel implementation must keep (each is a test in `src/mocks/analytics.test.ts` or
`src/lib/analytics/series.test.ts`):

- **Money in centavos**, integers only. Formatting happens in the browser.
- **Sales = payments collected**: every payment not voided, on the Manila day of `paid_at`. For the
  same range, the dashboard KPI, the sales report total, the payments report total and
  `GET /payments` `meta.collected_cents` are equal to the centavo.
- **Revenue by service** splits each payment across its order's lines in proportion to their
  subtotals, by the largest-remainder method (`allocate()`), so it adds up to sales exactly.
- **Days are Manila days**: group by `DATE(CONVERT_TZ(col, '+00:00', '+08:00'))` when timestamps
  are stored in UTC. Days with nothing are returned as zero (averages as `null`).
- **Staff never receive money.** For a user without `sales.view`, `/analytics/dashboard` returns the
  staff shape, built without any peso field; `/reports/*` answers 403.
- Insights are the fixed rules in `src/lib/analytics/insights.ts`, not generated text.

Suggested queries (MySQL 8, timestamps stored in UTC; `@tz = '+08:00'`):

```sql
-- Sales by day
SELECT DATE(CONVERT_TZ(paid_at, '+00:00', @tz)) AS day, SUM(amount_cents) AS sales_cents
FROM payments
WHERE voided_at IS NULL
  AND paid_at >= CONVERT_TZ(:from, @tz, '+00:00')
  AND paid_at <  CONVERT_TZ(:to + INTERVAL 1 DAY, @tz, '+00:00')
GROUP BY day;

-- Drop-off heatmap (0 = Monday)
SELECT WEEKDAY(CONVERT_TZ(received_at, '+00:00', @tz)) AS weekday,
       HOUR(CONVERT_TZ(received_at, '+00:00', @tz))    AS hour,
       COUNT(*) AS orders
FROM orders WHERE received_at BETWEEN :start AND :end GROUP BY weekday, hour;

-- Turnaround: first time each order reached Ready for pickup (status 5)
SELECT o.id, TIMESTAMPDIFF(MINUTE, o.received_at, MIN(h.changed_at)) / 60 AS hours,
       DATE(CONVERT_TZ(MIN(h.changed_at), '+00:00', @tz)) AS ready_day
FROM orders o JOIN order_status_history h ON h.order_id = o.id AND h.to_status_id = 5
GROUP BY o.id HAVING ready_day BETWEEN :from AND :to;

-- New vs returning: a customer is new in the week of their first order
WITH firsts AS (SELECT customer_id, MIN(received_at) AS first_at FROM orders GROUP BY customer_id)
SELECT YEARWEEK(CONVERT_TZ(o.received_at, '+00:00', @tz), 3) AS week,
       COUNT(DISTINCT CASE WHEN YEARWEEK(CONVERT_TZ(f.first_at, '+00:00', @tz), 3)
                                = YEARWEEK(CONVERT_TZ(o.received_at, '+00:00', @tz), 3)
                           THEN o.customer_id END) AS new_customers,
       COUNT(DISTINCT o.customer_id) AS all_customers
FROM orders o JOIN firsts f USING (customer_id)
WHERE o.received_at BETWEEN :start AND :end GROUP BY week;
```

Allocating payments to services is easiest in PHP (a port of `allocate()`) over
`payments JOIN order_items` for the range. At this shop's size every report is a few thousand rows;
cache a response for 60 seconds per range and role if needed.

Indexes these queries need:

- `payments (paid_at, voided_at)`, `payments (order_id)`, `payments (received_by, paid_at)`
- `orders (received_at)`, `orders (customer_id, received_at)`, `orders (current_status_id, promised_at)`,
  `orders (received_by, received_at)`
- `order_status_history (order_id, to_status_id, changed_at)`, `order_status_history (changed_by, changed_at)`
- `order_items (order_id, service_id)`
- `inventory_movements (item_id, moved_at)`

**Removed:** `GET /orders/{id}/receipt`, `GET /orders/lookup`, `GET /public/track/{token}`,
`POST /public/track/lookup`. Do not build them.

### Phase 2 checklist

The plan the Laravel API was built from, kept for reference. Where the build differs, the build
wins: authentication is **JWT** with two guards (`api` for staff, `customer`), not Sanctum or
sessions; a basket that holds another order answers **409**, decided under the basket lock with the
day's order sequence locked first. See `../laravel-backend/README.md` and `../docs/API_INVENTORY.md`.

**Tables and migrations**

- `customers.contact_number`: normalize to `09XXXXXXXXX`, then `UNIQUE`. The seed has no duplicates;
  check real data before adding the index.
- `customer_accounts`: `id`, `customer_id` FK `UNIQUE` (cascade restrict), `email` `UNIQUE` (store
  lower-case), `password` (hash), `is_active` bool default true, `must_change_password` bool default
  false, `last_login_at` nullable, `remember_token`, timestamps.
- `baskets`: `id`, `basket_number` `UNIQUE` (`BSK-0001`), `qr_token` `CHAR(32)` `UNIQUE`
  (`Str::random(32)`, never regenerated), `label` nullable, `status` enum
  `available|in_use|retired`, `notes` nullable, `created_by` FK users, timestamps. No `order_id`.
  No delete route; no `SoftDeletes` needed because retired rows stay.
- `order_baskets`: `id`, `order_id` FK, `basket_id` FK, `assigned_at`, `assigned_by` FK users,
  `released_at` nullable, plus
  `active_flag TINYINT AS (IF(released_at IS NULL, 1, NULL)) STORED` and
  `UNIQUE(basket_id, active_flag)`: MySQL allows many NULLs, so a basket has at most one open row.
  Index `(order_id)`.
- `customer_notifications`: `id`, `customer_id` FK, `order_id` FK, `type` enum
  `order_received|status_changed|ready_for_pickup`, `message`, `sent_at`, `read_at` nullable.
  Index `(customer_id, read_at)`.
- `order_statuses`: change the label of `released` to `Completed`; keep the code.
- `orders.qr_token`: from the original plan, no longer used. Do not create it, or drop it.
- `shop_settings.receipt_footer` is now the closing note of the Order Summary (rename optional).

**Basket status approach.** `baskets.status` is stored and kept in sync inside the same transaction
as each assignment and release. The `UNIQUE(basket_id, active_flag)` index is the real guarantee.

**Transactions with locking**

- `POST /orders`: `DB::transaction`, then `Basket::whereIn('id', $ids)->lockForUpdate()->get()`,
  re-check each is not retired and has no open `order_baskets` row, then create the order (status
  Received), items with `unit_price_cents` copied from the service, the `order_baskets` rows, the
  first `order_status_history` row, the audit log, the optional payment and the
  `order_received` customer notification. Catch the unique-index violation as a 409 (built: "One of the baskets was just taken by another
  order. Choose again.").
- `POST /orders/{id}/status`: lock the order row; run the same `checkTransition` rules; write
  history, audit and the customer notification; on `released`, set `orders.released_at`, set
  `released_at` on its open `order_baskets` rows and their baskets to `available`, all in one
  transaction.
- `POST /baskets/{id}/retire`: lock the basket, 409 if an open assignment exists.
- `POST /baskets`: lock the table's last number (or use a sequence row) so two admins cannot get
  the same number.

**Guards and sessions**

- Keep `web` for staff (`users`). Add a `customer` session guard with a `customers` Eloquent
  provider on `CustomerAccount` (`Authenticatable`). With Sanctum SPA auth, add
  `'guard' => ['web', 'customer']` in `config/sanctum.php`, protect staff routes with
  `auth:sanctum` + a check that the user is a `User`, and customer routes with `auth:customer`.
  A customer session must get 401 on every staff route and the reverse (see `portal.test.ts`).
- `customer/auth/login` uses `Auth::guard('customer')->attempt()`, regenerates the session and
  refuses `is_active = false`. Logout invalidates only that guard.
- Middleware `EnsurePasswordChanged` on customer routes: 403 while `must_change_password` is set,
  except `me`, `logout` and `account/password`.

**Policies and abilities**

- New abilities `baskets.manage` (admin) and `baskets.scan` (admin and staff; replaces `qr.scan`)
  in the role/ability map. They are base abilities, not staff toggles.
- `BasketPolicy`: `viewAny/view/scan` → `baskets.scan`; `create/update/retire` → `baskets.manage`.
- `CustomerOrderPolicy` or a scoped query: every `/customer/*` query is
  `->where('customer_id', auth('customer')->user()->customer_id)`, and a miss is 404 via
  `firstOrFail()`, never 403.
- Customers have no write access to orders, payments, prices or baskets.

**Rate limits**

- `RateLimiter::for('customer-login', fn ($r) => Limit::perMinute(5)->by(strtolower($r->email).'|'.$r->ip()))`
  counting failed attempts only, 429 with a message. Also throttle `register`.

**Counter registration and temporary passwords**

- `POST /customers`, `POST /customers/{id}/account`, `POST /customers/{id}/reset-password`
  generate a 10-character temporary password (letters and digits), store only `Hash::make()`, set
  `must_change_password = true`, and return the plain value once in the response. Never log it.
- Form requests mirror `lib/accounts.ts`: email `email:rfc` + `unique:customer_accounts,email`
  (lower-cased first), password `min:8` + letters + numbers + `confirmed`, name trimmed and required,
  phone normalized then `regex:/^09\d{9}$/` + `unique:customers,contact_number`. Registration with
  a phone on a legacy profile answers 422 "This number is already on file. Please ask the shop to set
  up your account." and creates nothing.

**Seeders.** 70 baskets (2 retired), 120 days of orders with their items, payments, status history
and supply movements, an account for every customer with orders, 3 legacy profiles, and basket
assignments for active orders. Port `mocks/seed.ts` (it is deterministic) so the Laravel demo shows
the same charts.

## Limits of the mock (Phase 1)

- **Cross-device needs Phase 2.** The data lives in one browser's `localStorage`, so a phone cannot see
  an order created on the shop's computer. The whole flow (staff, customer, scan) works on one device:
  open `/b/<token>` from a printed label preview, or type `BSK-0001` in the scanner.
- **The demo build has no offline app shell**, because MSW owns the service worker (see "Service
  workers: demo build vs real API"). Offline behaviour is tested on the real-API build.
- **The camera and the mock both need HTTPS or localhost.** A phone opening `http://192.168.x.x` gets a
  message saying so instead of the app. Deploy with HTTPS in Phase 2.
- **QR decoding on browsers without a native `BarcodeDetector`** (desktop Chrome, Firefox, Safari) downloads a
  WebAssembly decoder from a CDN the first time. It needs internet access unless self-hosted.
- **Basket labels have been checked in print preview, not on a physical label sheet.** Sizes are in
  `index.css` (`.label-page`, 3 × 8 of 64 × 34.5 mm on A4). Adjust them to the label stock you buy.
- **The mock has no client IP**, so the sign-in rate limit is per email only.
- **Staff permission changes** reach a signed-in staff member's menus on their next page load, while the API
  enforces them immediately.
- **The barangay list** in `mocks/seed.ts` (36 barangays) was checked against Wikipedia, not a government source.
  Confirm it against the municipality's list before seeding MySQL. The service rates and the shop contact number
  are placeholders.
